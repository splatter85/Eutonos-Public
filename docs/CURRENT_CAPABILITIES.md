# Current Capabilities

This document describes complete workflows the portable ToVA Project Workflow package can currently support. Concrete files, tools, fixtures, templates, and modules are inventoried in `CURRENT_FEATURES.md`; construction and responsibility boundaries belong in `ARCHITECTURE.md`.

## Safely Inspect, Install, And Upgrade A Project Workflow

A project can be inspected without writes at one explicit root, classified, given deterministic structural and semantic plans, reconciled toward the current ToVA baseline without losing project truth, and finalized only after accepted migration and target-local evidence exist.

- Inputs: an existing or blank repository plus the portable workflow package.
- Process: discover owners, casing, semantic candidates, version chain, and nested roots; review the exact plan and content-level ledger; bootstrap create-only; reconcile; retire only accepted exact sources; run migration and project gates; then finalize.
- Guidance: one setup owner routes blank, established, legacy, and upgrade cases through full-core evaluation, labeled uncertainty, target-local proof, finalization, and normal use.
- Outputs: installed workflow owners, an installation identity only after acceptance, and separate migration/preservation evidence.
- Evidence: F1-F7 disposable fixture campaign, adversarial failure boundaries, workflow and migration checkers, installer tests, and rc.10 mirror/checksum proof.
- Limits: semantic suggestions do not decide project meaning; the package does not approve, publish, or accept a target automatically, and destructive conflicts stop before writes.

## Orient An Agent And Confirm Project Definition

An agent can start from compact owners, avoid active-work collisions, and conduct a conditional five-question discovery conversation when project purpose or architecture remains unconfirmed.

- Inputs: installed Agent Start, boot, state, task, work model, health, and discovery owners.
- Process: read the ordered boot set, inspect repository evidence, ask only unresolved grouped questions, offer labeled evidence-based options, and write confirmed answers to durable owners.
- Outputs: an evidence-grounded project definition without a competing answer ledger.
- Evidence: installed-only cold-start fixture audits and five-question contract tests.
- Limits: suggestions remain assumptions until the user confirms them.

## Carry An Idea Through Bounded Work And Truthful Promotion

A team can distinguish desired outcomes from proposed mechanisms, admit one coherent Slice or Campaign, execute from a sole live board, verify proportionally, and promote only proven truth.

- Inputs: Future Capabilities or Future Features plus project evidence.
- Process: plan, record the live checklist in Current Task, execute one Slice or Sub-slice, run Project Health, then update Current Features, Current Capabilities, Architecture, state, or history only when their truth changed.
- Outputs: bounded completed work with explicit evidence, limitations, and remaining scope.
- Evidence: Work Model, TOVA Help, planning templates, starter tests, and workflow checks.
- Limits: a plan, checked box, structural scaffold, or successful build alone is not a supported capability or release approval.

## Continue Bounded Work Across Environments

A team can carry one compact execution pointer across GitHub, ChatGPT, Codex, other agents, and local machines while keeping detailed history and proof in Git rather than chat.

- Inputs: durable Execution State, safe Development Nodes, Current Task, current owners, and an exact source revision.
- Process: move one writer lease along a shared serial branch or isolate parallel writers on distinct branches/checkouts; use checked repository routes and compact/expanded cold-agent packets; keep Action progress volatile; record sparse Notes; test one exact source revision; and return through a versioned Exchange plus integration review.
- Outputs: reviewable cross-environment continuation with owned paths, bounded authority, adaptive context, exact evidence refs, and explicit returned/integrated boundaries.
- Evidence: collaboration checker and focused state, Note, and Exchange regressions.
- Limits: this is a repository-owned coordination contract, not a scheduler, controller, shared service, autonomous branch manager, or ATLAS implementation.

## Transfer Work And Retain Useful Outputs

People and agents can create bounded generic handoff packages or execution Exchanges for an explicit receiver, select a compact/expanded context profile, and retain non-handoff analyses or exports without turning any of them into competing truth owners.

- Inputs: current owner references and an explicit transfer or retention purpose.
- Process: record provenance, scope, checks, limitations, sensitive-data boundaries, and lifecycle; verify archives when packaging a transfer.
- Outputs: reviewable handoffs or retained work products that link back to current truth.
- Evidence: handoff/output owner contracts and mirrored starter tests.
- Limits: neither path implies installation, acceptance, publication, or release.

## Assure A Maintained App Contract When Explicitly Enabled

The optional app-build-assurance module can validate whether a maintained app contract names its product workflow, architecture, data/recovery, quality, lifecycle, review lenses, and referenced evidence.

- Inputs: an enabled module and an app-local assurance contract with evidence refs.
- Process: validate schema and references, then fail closed on unsafe or unsupported claims.
- Outputs: structural assurance findings.
- Evidence: module example and executable checker tests.
- Limits: the module is disabled by default; structural success is not runtime, device, privacy, migration, human, beta, or release acceptance.

This remains an unpublished release candidate. Owner approval, publication, target installation, and portable-baseline acceptance are separate decisions.
